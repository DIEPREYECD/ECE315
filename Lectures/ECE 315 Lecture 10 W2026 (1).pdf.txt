Protection of Critical Sections ­ Semaphores & Mutexes

· Mutexes and semaphores are synchronization primitives
· are tools used in multitasking embedded RTOSes · coordinate access to shared resources and control task execution order
· A semaphore is a counter-based synchronization object that controls access to a shared resource by counting available slots or permissions.

· A mutex is like a binary semaphore but designed specifically for mutual exclusion -- ensuring only one task at a time can access a shared resource (like a UART, sensor, or global variable)

Without synchronization, race conditions, data corruption, or deadlocks can occur.

Mutexes and Semaphores

Typical Use of a Mutex
1. Create a mutex at system startup. 2. Before a task uses the shared resource, it takes (locks) the mutex. 3. After using the resource, it releases (unlocks) the mutex. 4. If another task tries to lock it while it's in use, it blocks until the mutex becomes available.

Typical Use of a Semaphore
1. One task (or ISR) "gives" the semaphore to signal an event. 2. Another task "takes" the semaphore and continues when the signal is received. 3. Often used for event notification or task synchronization.

Synchronization via a Queue

Tasks (e.g., one producer task and one consumer task) synchronize through the transfer of data.
· This is often conveniently implemented using a queue.
1. The producer task sends data to the consumer task by adding/writing data to the back end of a queue.
2. The consumer task calls a blocking receive function that attempts to read data from the front of the queue.
· If data is immediately available in the queue, then the consumer task can proceed and process the new data.
· If there is no data present in the queue, then the consumer task is switched off the CPU and is added to the queue of tasks that are blocked on the queue.
· Later, when data is added to an empty queue, the highest priority task that is blocked on the queue becomes ready-to-run.

Deadlock
· Is a situation where two or more tasks are permanently blocked, each waiting for a resource (such as a mutex, semaphore, or message queue) that can only be released by another blocked task
· As a result, none of the tasks can proceed, and the system or part of it becomes frozen indefinitely

Deadlock

· Edward Coffman's conditions (which apply to general and embedded systems), a deadlock can occur if all four of the following are true:
· Mutual Exclusion ­ Resources cannot be shared (only one task at a time can use them).
· Hold and Wait ­ A task holds one resource while waiting for another. · No Preemption ­ Resources cannot be forcibly taken away.
· Circular Wait ­ A circular chain exists where each task holds one resource and waits for another.
· Breaking any one of these conditions prevents deadlock.

Priority Inversion

· Related to Deadlock is the situation called Priority Inversion.
· It is a condition where a high-priority task is indirectly blocked by a lower-priority task, due to a shared resource (e.g., a mutex) being held by that lower-priority task
· As a result, a medium-priority task (that does not depend on the shared resource) can preempt the low-priority one -- causing the high-priority task to wait even longer.
· This inverts the intended priority order: the low-priority task effectively delays a high-priority task.

Adapted from ECE 315 W2025 by Dr. Bruce Cockburn

How Priority Inversion Happens...

1. Low-priority task (L) locks a shared resource (e.g., a UART protected by a mutex).
2. High-priority task (H) becomes ready and tries to lock the same resource -- but must wait because L holds it.
3. Medium-priority task (M) that doesn't need the resource becomes ready and, since it has higher priority than L, it preempts L.
4. L can't finish and release the resource, so H remains blocked -- even though H has the highest priority.
The system's behavior now effectively inverts priorities:
H (highest) < M (medium) < L (lowest).

Solutions to Priority Inversion

· Complicated to find safe ways of forcing a low-priority task to give up exclusive access to a resource in a critical section.
· A common strategy for solving the priority inversion problem is to temporarily raise the priority of the low-priority task to at least the priority of any high-priority task that gets blocked on the semaphore that controls allocation of the contested resource. This allows the low-priority task to finish using its resources quickly so that the high-priority task can proceed. Medium-priority tasks cannot interfere.
· FreeRTOS provides mutual exclusion semaphores (mutexes), which are binary semaphores that cause the priority of the semaphore-holding task to be raised to that of any higher priority task that gets blocked on the same semaphore.

Watchdog Timers

· A watchdog timer (WDT) is a hardware or software timer used to detect and recover from software malfunctions,
· e.g., such as one task hogging the CPU, multitasking deadlock, memory leak, etc.
· It acts like a safety mechanism that ensures the system keeps running properly.
· If the software fails to "pet" (reset or refresh) the watchdog timer within a specified time period, the watchdog assumes the system is stuck or malfunctioning and forces a system reset or other corrective action
· They can be dangerous ­ a faulty hardware or software WDT can result in a fast, infinite reset loop ("death loop") that is hard to debug
