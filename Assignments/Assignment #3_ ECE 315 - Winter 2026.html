You are asked to design an embedded microcontroller system that managed a voltage-controlled oscillator (VCO) made by Skyworks.

The system needs to do the following:

  • manage the reference voltage to the VCO, including measuring it
    • the reference voltage sets the frequency the VCO outputs
  • measure the temperature near the VCO using a thermistor so that the effect of temperature can be compensated,
  • display the current temperature and VCO reference voltage, and
  • transfer status and other information to a bluetooth module that will update a smartphone app.

The VCO output frequency is allowed to vary by up to 1 ppm per minute. You may assume the VCO can respond to a change in reference voltage within microseconds.

You are to use the following components;

  • A Skyworks Si595 Download Skyworks Si595voltage-controlled crystal oscillator,
  • A Texas Instruments DAC60501ZDGSR Download DAC60501ZDGSR,
  • A TDK NTCGS103JF103FT8 Download NTCGS103JF103FT8 thermistor,
  • A Display Visions 0.96" TFT display panel,Download 0.96" TFT display panel,
  • A Fanstel BT832A Bluetooth moduleDownload BT832A Bluetooth module

The microcontroller is the RP2040 .

Create a block diagram showing all the connections to components listed. Clearly label each component and the interface to the RP2040. Don't forget to indicate which pins on a device are used.

Be sure to include the address of any peripheral on an I2C bus. Make sure that either 3-wire or 4-wire SPI is indicated if SPI is used.

For the thermistor assume it is one resistor in resistor divider, the other being a 1% 10kΩ.  

Provide a written justification for each interface selected, why it is appropriate, how it meets the system requirement. This can be in bullet point format.

Put all of this in a PDF and name it "ECE 315 Assignment 3 System Design", then submit.

Marks will be deducted if the document is not well-organized and neatly written. Use a drawing package like https://app.diagrams.net/ .

 

Your Answer:

ECE 315 Assignment 3 System Design.pdf

Find my design attached in the pdf file above. 

The RP2040 acts as the central controller of the system, reading temperature and reference voltage using its ADC inputs. The DAC60501 is controlled via I2C to generate the analog voltage that drives the Si595 VCO control pin, allowing the oscillator frequency to be adjusted. A thermistor voltage divider provides temperature measurements used for compensation. The TFT display is connected via SPI to show the current temperature and reference voltage, while the BT832A Bluetooth module communicates with the RP2040 over UART to transmit system status information to a smartphone application.

This system is relatively slow in terms of time to change or respond, so unless it's not possible, a slower I2C interface tot he DAC, display, and BT832A module can be used.

The block diagram should show

  • the main power voltage of 3.3 VDC,
  • the voltage from the thermistor-resistor divider input to the RP2040 ADC input (one of pins 38, 39, 40, or 41)
  • the reference voltage is provided by the DAC
    • the reference voltage provided by the DAC is measured by the RP2040 ADC input (one of pins 38, 39, 40, or 41)
    • because the output frequency can vary up to 1 ppm / minute, the ADC, which can sample up to 500 ksps, is more than fast enough.
  • the appropriate RP2040 pins for I2C and SPI when either or both are used
  • the Vc pin (pin 1) of the VCO connected to the output voltage of the DAC (pin 2)
  • if configured for I2C, the DAC I2C address of either 0x48, 0x49, 0x4A, or 0x4B
  • the BT832A interface to the RP2040 should be SPI or I2C,
    • if the BT832A is configured as an I2C peripheral, it can have any 7-bit I2C address as that is programmable
  • if there is another peripheral connected to the RP2040 via SPI, the TFT display interface is 4-wire SPI with a chip select line. Otherwise it can be a 3-wire interface
  • if the TFT display is configured for the touch interface, it will be an I2C peripheral with address is 0x70

In terms of which interfaces to the RP2040 are appropriate, since this is a slow system, the following interfaces are preferred;

  • RP2040 <-> BT832A should use SPI. The use of a chip-select signal is optional since this should be the only SPI interface. A wise designer would keep chip-select just in case the design is updated in future with another SPI device
    • Rationale for SPI is that Bluetooth supports up to 64 Mbps, so data rates between the RP2040 and BT832A would exceed the normal limits of I2C
  • RP2040 -> DAC should use I2C because the VCXO frequency change rate is pretty slow
    • Rationale is that the VCXO frequency changes are relatively slow
  • RP2040 <- thermistor uses the RP2040's built-in ADC and is an analogue interface
    • Rationale is that this is the only interface possible. If this rationale is not mentioned, no marks off, it's kind of obvious
  • RP2040 <-> TFT display must use SPI to send data for the panel to display. If the designer chooses to enable a touch feedback mechanism, that will be via I2C
    • Rationale is that only SPI is supported by the display. I2C is needed only if touch is enabled. No marks off if I2C is not mentioned

Marks breakdown

  • 0.4 for complete block diagram showing all the components listed
  • 0.2 for having pins correctly listed for all the component data connections (they may be inside the boxes used to represent the components), except for the thermistor and DAC output (the ADC input pin on the RP2040 must be listed)
  • 0.3 for listing the rationale for the interface choices. if not all interfaces listed, then 0.1 marks
  • 0.1 for listing I2C addresses

In Wokwi, create a Raspberry Pico C/C++ SDK project that has a custom analogue output chip that generates pseudo-random numbers and outputs them as voltage between 0 and 1 volts.

Refer to Lecture 17 for the FreeRTOS and SPI example. You don't have to use FreeRTOS for this assignment question.

The output of the custom chip is sampled once per second by the Pico's built-in ADC and the value output to a second custom chip that has an SPI interface. We can imagine the second custom chip to be a display of some kind, but for this assignment we will only output (printf())what it receives to the custom chip console.

Begin by reading the Wokwi reference for custom chips. Pay attention to the custom chip console discussion.

For the SPI custom chip that is the output device, in the Wokwi reference for custom chips look at the SPI device API, and I suggest looking at the example.

In general, follow these steps;

  1. Create a blank Pi Pico SDK project in Wokwi.
  2. Save it with the name "ECE 315 Assignment 3 <CCID>" where you replace <CCID> with your CCID. Make sure to make the project public.
  3. Add a custom chip named noise-maker and set the language to C.
  4. Modify it to have only pins VCC, GND, and OUT by editing noise-maker.chip.json.
  5. Change noise-maker.chip.c to implement the pseudo-random noise generation.
    • One way to generate a random number is to use   float rnum = (float) rand() / (float) RAND_MAX ;
  6. Connect the noise-maker chip to the Pico being sure to connect its OUT pin to one of the ADC-capable pins on the Pico.
  7. Set up the main.c file to enable the ADC and sample the noise-maker signal once per second and printf() the result.
  8. Next create a second custom chip and name it something like my-output-display
    • Modify it to have SCK, SDI, and nCS pins by editing its json file
  9. Program my-output-display to behave like an SPI peripheral and only receive data (it has no SDO pin/signal)
  10. Have my-output-display buffer received bytes until a new line character is received. When that happens, have it printf() the buffer and reset it.
  11. Test your program and make sure that there is output from main.c and from my-output-display.
  12. Be sure your source files are nicely documented including a suitable file header.
    • Failure to do so will result in marks reduction.
  13. In Wokwi, select the Share menu and copy the link to your project.
  14. Submit that link.

Marks will be deducted for messy code, for incorrect implementation, and not following the file and project naming guidelines.
