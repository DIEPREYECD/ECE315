Consider the design of a system to sample a small-peak amplitude system. You are given a 12-bit ADC that has full-scale range of 3.3 volts. The actual maximum input signal amplitude is 10 mv peak-to-peak. 

  1. Estimate the number of effective bits used by the input signal
  2. Propose two hardware-based modifications to improve measurement accuracy
  3. Is there something that can be done in software to improve measurement accuracy?
Your Answer:

A 12-bit ADC with a full-scale range of 3.3 V has an LSB size of:

LSB = 3.3 / 212 = 3.3 / 4096 ≈ 0.0008057 V = 0.806 mV

The input signal is 10 mV peak-to-peak, so the number of ADC counts used by the signal is:

10 mV / 0.806 mV ≈ 12.4 counts

The number of effective bits used by the signal is:

log2(12.4) ≈ 3.63 bits

So, the input signal uses only about 3.6 bits, which is roughly 4 effective bits of the ADC's 12-bit range.

Two hardware-based modifications to improve measurement accuracy

  1. Amplify the input signal before the ADC.
  2. Use a higher-resolution ADC or a programmable gain front end.
    A 16-bit or higher ADC would provide finer voltage resolution and allow the small signal to be measured more accurately.

Software-based improvement

Yes. A software technique we can use is oversampling and averaging because it improves measurement accuracy.

  • Take many ADC samples of the same signal
  • Average them together
  • This reduces random noise and can improve effective resolution

A) The resolution of the ADC is 3.3V / 2^12 = 805.7 µV/level

A 10 mV peak-to-peak signal will span 10 mV / 805.7 µV/level = 12.412 levels

That is equivalent to log2(12.412) = effective 3.63 bits.

That means that we are not using 12 - 3.63 = 8.37 bits of the ADC

B) If we know that we will never have more than 10 mV peak-to-peak input, we can use an opamp to amplify the signal to close to 3.3 V peak-to-peak and make better use of the ADC's range. That will improve the resolution from 805.7 µV to 2.44 µV.

We might also change to an ADC with programmable gain, which is another way to amplify the input

C) If the signal can be oversampled, we would gain about 1 bit for every 4x oversampling. Obviously this doesn't scale well and will increase the cost of the ADC, add complexity in terms of anti-aliasing and noise control

Some trade-offs:
•    Amplification increases noise bandwidth and requires careful filtering
•    Higher resolution ADCs reduce speed and increase cost
•    Oversampling increases CPU/DMA load

 

-----------

 

 

Key Points for a Good Answer

  1. Correct ADC Resolution Calculation

    • Determine LSB size:

      3.3V/2^12 ~= 806 µV per level

    • Use this to relate signal amplitude to quantization levels.

  1. Proper Estimation of Effective Bits

    • Compute number of levels used by the signal (~12 levels).

    • Convert to bits using ( log_2[ ] ), yielding ~3.6 effective bits.

    • Recognize that most of the ADC resolution is unused.

  1. Insight Into Dynamic Range Mismatch

    • Identify the core issue: signal amplitude is far smaller than ADC full-scale range.

    • Explain how this leads to poor effective resolution and high quantization error.

  1. Hardware Improvement via Signal Conditioning

    • Propose amplification (e.g., op-amp) to scale the signal to near full-scale.

    • Mention alternative: programmable gain ADC.

    • Recognize this improves effective resolution significantly.

  1. Software-Based Improvement (Oversampling)

    • Explain oversampling and averaging (≈ +1 bit improvement per 4× over-sample).

    • Acknowledge diminishing returns and increased system load.

  1. Trade-off Awareness and System-Level Thinking

    • Amplification increases noise and requires filtering

    • Higher-resolution ADCs increase cost and may reduce speed

    • Oversampling increases CPU/DMA requirements

You are given the task to create a system to sample four (4) analogue channels at 10 kSps each. You are given a microcontroller with one core that is clocked at 250 MHz

You may assume you have independent ADCs; that is either four ADC peripherals built into the microcontroller or there are four external ADCs each with their own dedicated interface to the microcontroller. 

  1. Compare DMA-based acquisition vs interrupt-driven sampling.
  2. Estimate CPU utilization in both approaches (assume 2 µs ISR overhead).
  3. Argue which approach is more robust for real-time control and why, referencing system constraints .
Your Answer:

Sampling System Comparison

Four channels at 10 kSps each gives a total sampling rate of:

4 × 10,000 = 40,000 samples/s

Interrupt-driven sampling

If each sample causes an interrupt, then the system must handle 40,000 interrupts/s. With 2 µs ISR overhead per interrupt:

40,000 × 2 µs = 80,000 µs = 0.08 s per second

CPU utilization:

0.08 / 1.0 × 100% = 8%

DMA-based acquisition

With DMA, data transfer is handled by hardware, so the CPU is only needed for setup and occasional buffer handling. Thus, the CPU cost for acquisition is very small / negligible compared to interrupts.

Robustness?

DMA-based acquisition is more robust for real-time control. It reduces CPU load, avoids a high interrupt rate, lowers timing jitter, and reduces the chance of missed samples. This leaves more CPU time available for control tasks on the 250 MHz single-core microcontroller.

A) The interrupt approach is probably simple to program. The ADCs are independent, we we have independent ISRs. Each can transfer and save ADC samples to specific memory ring buffers A simple counter will tell the ISR when to jump from the end of the buffer to the beginning.

By comparison, the DMA approach is more complicated to set up and design choices like how big to make the buffer and how many samples to transfer at a time need consideration. We probably have to use a ring buffer, which is more complicated because we will transfer multiple samples per DMA transaction.

B) Consider the ISR approach. Assume an interrupt for every new sample.

That means 40,000 interrupts per second, which results in 40,000 * 2 µs  = 80 ms of CPU time every second, which is at least 80 ms / 1000 ms * 100 = 8% of the CPU capacity. This is assuming that the number of cycles needed for the ISR is not too high, that at 250 MHz the CPU is fast enough.

That many interrupts every second may introduce jitter and latency for other CPU operations, and will make programming it more complicated. If it's running an RTOS, it may interfere with the determinism of the RTOS tasks. 

There is also some loss of bus bandwidth as each sample has to be transferred by the CPU to its buffer, meaning other tasks get less time to use the bus.

Now consider the DMA approach. Once initialized, there will be effectively zero overhead since multiple samples (>> 1)  are transferred per transaction. The big advantage is that the CPU is freed from the task. Of course, there may be some bus contention with the CPU.

C) There are trade-offs:

  • DMA setup complexity
  • Bus contention with CPU

But, overall, DMA is superior for real-time control because it reduces CPU load and jitter, enabling predictable timing required in embedded systems

-----------

 

Key Points for a Good Answer

  1. Clear Comparison of Programming Complexity

    • Interrupt-driven sampling is simpler (independent ISRs, straightforward ring buffers).

    • DMA requires more careful design (buffer sizing, batching, configuration complexity).

  1. Correct Throughput and Interrupt Rate Reasoning

    • Recognize total sampling rate = 4 × 10 kSps = 40 kSps.

    • Identify that this leads to 40,000 interrupts per second in ISR-based design.

  1. Accurate CPU Utilization Calculation

    • Compute CPU load:

    • 40,000 * 2µs = 80 ms -> ~ 8% of CPU (80/1000 =0.08)

    • Interpret this as non-trivial overhead, not just a number.

  1. Impact on Real-Time Performance (ISR Approach)

    • High interrupt rate introduces jitter, latency, and scheduling interference.

    • Can degrade RTOS determinism and responsiveness.

  1. DMA Advantages and System-Level Effects

    • DMA transfers multiple samples per transaction → minimal CPU involvement after setup.

    • Frees CPU for control tasks and improves timing predictability.

    • Acknowledge possible bus contention with CPU.

  1. Balanced Trade-off and Justified Conclusion

    • Recognize DMA drawbacks (complexity, design effort).

    • Conclude DMA is more suitable for real-time control systems due to:

      • Lower CPU load

      • Reduced jitter

      • Better determinism

  • GPA5 → DIR_3
  • GPA6 → STEP_4

  • GPB5 → MS3_1, MS3_2, MS3_3, MS3_4

d) Justification

Each motor has its own STEP and DIR signal, so direction, speed, and actuation are independent. Shared lines are acceptable because the requirements allow nSLEEP, nRESET, nENABLE, MS1, MS2, and MS3 to be common. One MCP23S17 is enough because only 14 outputs are needed.

Students can choose I2C or SPI for the MCP23x17.

Best choice is I2C. There is a small reduction in possible marks for specifying SPI.

I2C Answer

a) 0.2 marks : Use MCP23017 with the I2C interface

The reason for I2C is that (student answers should have at least two of these reasons)

  • it will run fast enough for the problem as stated
  • since there are already other I2C devices it is consistent
    • doesn't introduce a new interface
    • no new firmware/software needed
    • no new connections/PCB traces
  • keeps 2 of the 4 available Pico GPIOs available

b) 0.5 marks : Pico to MCP23017:

  • I2C interface RP-GP16 <-> MCP23017.SDA (13),
  • RP-GP17 -> MCP23017.SCL (12)
  • could also use GP18 and GP19 on Pico
  • A2 A1 A0 must be configured for I2C. They are allowed to be 0b000, 0b010 - 0b110 inclusive where 0 is GND, 1 is 3V3

c) 0.5 marks : MCP23017 to A4988s: Can be all sorts of combinations. Most efficient is to have the DIR and STEP connected to the same bank. Here it's bank B

  • GPA0 -> nSLEEP
  • GPA1 -> nRESET
  • GPA2 -> nENABLE
  • GPA3 -> MS1
  • GPA4 -> MS2
  • GPA5 -> MS3
  • GPB0 -> DIR_1
  • GPB1 -> STEP_1
  • GPB2 -> DIR_2
  • GPB3 -> STEP_2
  • GPB4 -> DIR_3
  • GPB5 -> STEP_3
  • GPB6 -> DIR_4
  • GPB7 -> STEP_4

d) 0.5 marks : We can use I2C because the data rate will support 65 RPM at 1/16 stepping mode. With 1.8 degrees per step, 200 full steps are needed for one revolution. At 1/16 microstepping, that means 16*200 = 3200 step signals for 1 revolution. In terms of RPM, that is 3200 * 65/60 =3,466.667 steps/second. A step needs a zero pulse and a 1 pulse. Assuming 50% duty cycle, that is 3466.6667*2 = 6,933.333 pulses. To run all motors simultaneously, we need to send 8 bits, changed by writing them to the MCP bank B. Thus we need to send 6933.333*8 = 55,466.664 bits/second. 

For I2C, we need in the worst case 29 bits to send 8 bits, so the full data rate needed is 55466.66 * 29/8 = 201,066.643 ~= 200 kSps. The I2C supports 400 kHz mode, so that works.
